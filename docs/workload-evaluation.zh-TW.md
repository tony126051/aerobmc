# BMC 三類工作初評

本頁保留 AeroBMC 局部架構實驗的初期評估，範圍為模擬最小可行核心的三類管理工作。 [專案定位](../README.md)

2026-11-11。評估優先順序為感測器與事件、風扇與電源控制、管理 API。第一類已有主機重播結果，後兩類已定義對照實驗與進入實測的條件。

| 工作 | ArceOS 可能改善的環節 | Linux 對照與判定 |
|---|---|---|
| 感測器與事件 | 固定容量資料結構、同位址空間的事件傳遞。實體取樣仍受裝置及匯流排等待影響。 | 在相同硬體與輸入下，先讓精簡 Linux 程式和 ArceOS 共用同一 Rust 核心。量測核心處理時間、取樣到事件消費的 p99 延遲、CPU 使用率及佇列丟棄。再以 OpenBMC 感測器及 D-Bus 路徑補上整體堆疊對照。 |
| 風扇與電源控制 | 排程喚醒與輸出命令提交可能縮短。PWM 更新、電源軌時序及 power-good 回饋取決於裝置。 | 兩端使用相同控制狀態機與模擬回饋。風扇記錄週期抖動、期限未達次數與命令到回饋的時間。電源記錄命令到 power-good 的時間、逾時及重試。實體測試需板級時序、回饋與保護規格。 |
| 管理 API | 讀取同一程序內的感測器快照可能減少 IPC。TLS、授權、序列化與網路也會影響總延遲。 | 先測單一唯讀感測器端點。固定 payload、TLS 設定、認證與授權規則、連線重用率及客戶端併發數，分別量測握手與既有連線請求的 p99、吞吐、錯誤率和記憶體。待兩端具備等效安全設定才比較。 |

## 感測器與事件重播

使用先前建置的 macOS ARM64 release 執行檔。每種輸入各重播 100 萬筆，邏輯時間從 0 開始，每筆遞增 1 ms。每組執行六次，捨棄第一筆結果。計時範圍含狀態更新、事件入列、出列及事件收集，不含 CSV 解析與列印。

| 輸入序列 | 每次事件數 | 五次總耗時中位數 | 範圍 |
|---|---:|---:|---:|
| 固定 70°C | 1 | 1.073 ms | 1.023–1.549 ms |
| 80°C／75°C 交替 | 1,000,000 | 4.803 ms | 4.671–5.238 ms |
| 讀取失敗／70°C 交替 | 999,999 | 4.924 ms | 4.872–5.324 ms |

每次重播的事件數均符合預期，丟棄數為零。原始六事件範例與預期 CSV 完全一致，既有三項核心測試執行檔也全數通過。重播器每筆操作後立即排空事件佇列。這些數字只描述單一感測器在 macOS 上的整批記憶體重播，尾延遲、實體取樣、控制週期以及 Linux／ArceOS 差距都尚待量測。本次暫存工具鏈的編譯器執行檔已不存在，使用既有產物完成驗證。

## 實測順序

1. 先在同一 AArch64 目標跑通 Linux 與 ArceOS 重播，核對事件序列，再加入單調時鐘與逐筆時間戳。QEMU 可用於驗證流程，硬體效能比較使用共同的實體目標。
2. 加入模擬 PWM／tach 與 power-good 後端，注入感測失效、回饋延遲和逾時，核對兩端狀態轉移後再量控制週期。
3. 等唯讀端點在兩端具備等效 TLS、認證與授權，再做管理 API 對照。若 ArceOS 與 G1 推論共用硬體，同時檢查推論尾延遲。
