# AArch64 QEMU 風扇與電源控制測試

本頁量測 AeroBMC 最小可行核心在模擬風扇與電源工作負載下的控制反應。 [專案定位](../README.md)

沿用單 vCPU 的 AArch64 QEMU TCG 機型與 13 ms 絕對週期，對照 Linux 與 ArceOS 的 100 Hz、1,000 Hz 組態。每次開機執行三種情境，每種 48 個控制週期，每組各開機三次。兩端使用同一份控制程式。各情境的 UART 輸出在該情境的計時區段之後。

| 模擬情境 | 輸入與判定 |
|---|---|
| 風扇失去轉速 | PWM 初始為 50%，模擬轉速 5,000 rpm。在 71.5 ms 停止回報。從第一次觀察到失聯開始計時，持續至少 26 ms 後切到 100% 保護 PWM。反應時間從注入失聯算起。 |
| Power-good 延遲後恢復 | 第一次無回饋。每次啟動最多等待 39 ms，逾時後關閉輸出，等待至少 26 ms 再試。第二次啟動 20 ms 後模擬 power-good。輪詢須在 39 ms 門檻前看見回饋。 |
| Power-good 持續缺失 | 三次嘗試均無回饋。第三次逾時後保持電源輸出關閉，並停在失敗狀態。 |

電源反應時間從首次啟用算到最終狀態。逾時超量為控制任務實際判定逾時的時間減去該次啟用後 39 ms。當輪詢同時看到回饋和已逾時，模擬控制器採逾時優先。週期抖動採相鄰兩次喚醒間隔與 13 ms 的絕對差，控制工作完成時間落在下一個釋放時間或之後即為逾期。

這些 PWM、轉速和時序值只用於故障注入。板上保護輸出、回饋來源、時序和逾時策略須依硬體規格決定。

## 結果

| 組態 | 控制週期抖動 p99 | 控制週期逾期 | 風扇保護反應範圍 | 最差電源逾時超量 | QEMU 主機 CPU 時間中位數 |
|---|---:|---:|---:|---:|---:|
| Linux（100 Hz 對照輪） | 3.37 ms | 0/432 | 35.36–48.45 ms | 15.36 ms | 1.011 s |
| ArceOS 100 Hz | 8.44 ms | 0/432 | 39.23–51.36 ms | 12.38 ms | 0.195 s |
| Linux（1,000 Hz 對照輪） | 3.63 ms | 0/432 | 35.36–36.05 ms | 13.82 ms | 0.949 s |
| ArceOS 1,000 Hz | 1.23 ms | 0/432 | 33.38–46.67 ms | 13.95 ms | 0.407 s |

每列有 432 個控制週期，扣除各情境首筆後有 423 個相鄰週期間隔供 p99 計算。正式量測的 12 次開機均切入風扇保護模式。延遲回饋情境都在第二次嘗試成功。持續無回饋情境都在第三次逾時關閉電源輸出。ArceOS 在 1,000 Hz 的週期抖動較低，模擬器 CPU 時間約為 100 Hz 的 2.1 倍。電源逾時超量沒有隨抖動一同改善，因為 39 ms 門檻只能在輪詢時判定。

正式量測前，100 Hz 曾有一次延遲回饋情境未通過預期成功的斷言。原測試器在輸出最終狀態前中止，因此該次無完整結果。測試器後來把合法的逾時失敗列為可記錄結果，保留輸出關閉與嘗試次數的檢查。正式量測中的獨立感測器週期測試也觀察到 ArceOS 100 Hz 有 2/768 次逾期，1,000 Hz 有 1/768 次。

板級設計需要確認 power-good 能否以 IRQ 或帶時間戳的回饋取得。如果只能輪詢，應把最長輪詢間隔納入 power-good 的時序預算，並根據硬體規格定義回饋和逾時同時被觀察到時的處理方式。

## 帶時間戳的 power-good

新增確定性重播來比較同一次輪詢下的兩種回饋。啟用時間為 0 ms，期限為 39 ms，任務到 45 ms 才處理回饋。若此時只看到高電位，會判定逾時。若記錄顯示本次嘗試在 20 ms 擷取到上升緣，且處理時電位仍為高，則判定啟動成功。擷取時間必須落在啟用時間（含）至期限（不含）之間，且不可晚於目前時間。

重播另涵蓋恰好在期限、晚於期限、電位已降回低、未來時間戳、關閉後才送達、前一次嘗試的事件、啟用前事件，以及本次重試的有效事件。關閉後收到的舊事件無法改回開啟狀態。所有案例使用合成時間戳驗證判定規則。

Linux 與 ArceOS 100 Hz 在相同 QEMU 設定下各開機三次，每次的十個案例均符合預期，合計 60 筆判定。既有六筆感測器事件及控制情境檢查也通過。逐筆結果存於 `results/qemu-power-good/power-good.csv`。

板級整合需取得電源啟用線與 power-good 的 GPIO／電源控制器映射、極性、IRQ 或擷取能力、時鐘來源和電源時序要求。接線時應在每次嘗試前清除待處理事件，確認輸出關閉期間的回饋狀態，並界定 IRQ 與逾時計時器同時發生時的同步規則。如果控制器只能在 ISR 進入時讀取時間，時間戳包含中斷延遲。若板規要求期限到達時立即切斷輸出，還需要獨立的期限處理，重播中的 45 ms 判定無法保證這項要求。

## 模擬 IRQ 與逾時計時器的交付順序

本專案以 QEMU 軟體模擬完成驗收。此次新增兩個獨立的控制入口，分別接收 power-good 邊緣事件與帶嘗試序號的逾時事件。測試用合成時鐘依序呼叫這兩個入口，讓相同時間點可重現兩種交付順序。

| 模擬條件 | 預期結果 |
|---|---|
| 20 ms 擷取到上升緣，45 ms 先處理 IRQ，再處理 timer | 接受準時擷取且仍為高電位的回饋，維持開啟 |
| 相同上升緣，45 ms 先處理 timer，再處理 IRQ | 逾時關閉，稍後處理的 IRQ 不改變輸出 |
| 上升緣恰好在 39 ms 或於 40 ms 出現 | 兩種交付順序均逾時關閉 |
| Timer 提早觸發、重複交付或前一次嘗試的 timer 在重試後才到 | 提早或過期的 timer 被忽略，重複交付不增加逾時次數 |
| 本次重試的有效 timer 到期 | 關閉輸出並增加逾時次數 |

目前選用先提交的有效狀態轉移生效。timer 已關閉輸出時，仍有原始時間戳的 IRQ 也不能使輸出重新開啟。這輪驗證事件交付順序及狀態轉移。後續也已使用 [QEMU PL061 驗證客體 IRQ 與逾時輸出](qemu-gpio-irq.zh-TW.md)。

Linux 與 ArceOS 各開機三次，每次 19 個回饋與事件順序案例，合計 114 筆結果均符合預期。原始結果位於 `results/qemu-irq-race/power-good.csv`，序列埠 log 同時保存感測器、週期和控制回歸結果。

## 重現

依 [AArch64 重播建置](qemu-replay.zh-TW.md) 和 [1,000 Hz 重建步驟](qemu-periodic.zh-TW.md) 產生兩個 ArceOS 映像。現在的 guest 會在感測器測試後執行控制情境。用同一 Linux initramfs 分別執行 `compare.py`，每輪指定新的輸出目錄。

結果含 `control.csv` 的逐週期時間、`control-outcomes.csv` 的最終狀態與次數、`power-good.csv` 的事件回饋重播結果，以及 `qemu-cpu.csv` 的每次 QEMU 主機 CPU 和牆鐘時間。主機 CPU 時間涵蓋整個 guest 開機與所有測試，可供比較模擬成本。板上中斷成本與功耗仍需硬體量測。

本機完整結果位於 `results/qemu-control-final-100hz/` 與 `results/qemu-control-final-1000hz/`。
